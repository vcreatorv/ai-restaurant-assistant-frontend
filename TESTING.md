# Сценарии тестирования

## Как запустить

### Режим с бэкендом (полная интеграция)
```sh
# Терминал 1 — поднять бэкенд
cd ai-restaurant-assistant-backend
make docker-up          # первый раз: занимает ~1 мин
make seed               # загрузить меню и фото

# Терминал 2 — запустить фронтенд
cd ai-restaurant-assistant-frontend
npm run dev
```

### Режим без бэкенда (мок-режим)
```sh
# Просто запустить фронтенд — бэкенд не нужен
cd ai-restaurant-assistant-frontend
npm run dev
```
При недоступном бэкенде приложение автоматически переходит в мок-режим:
отображается мок-профиль «Алексей Морозов», весь UI полностью работоспособен.

Открыть: `http://localhost:5173`

## Модуль: Чат (`/chat`)

### CHAT-1 — Загрузка активного чата

**Предусловие:** бэкенд запущен, юзер залогинен.

**Шаги:**
1. Открыть `/chat`

**Ожидаемый результат:**
- Сверху всегда видно приветственное сообщение «Здравствуйте, …! Помогу подобрать блюда…»
- Ниже — история сообщений из активного чата (если она есть)
- В DevTools/Network — запросы `GET /chats/active` и `GET /chats/{id}`
- В тексте ассистента **нет** ` ```json {...}``` `-блоков

### CHAT-2 — Стриминг ответа

**Шаги:**
1. Отправить сообщение «Что-то острое и лёгкое»

**Ожидаемый результат:**
- Появляется юзер-сообщение
- Typing-индикатор «…» до первого токена
- Текст ассистента появляется по мере прихода токенов; JSON-хвост не виден
- После завершения — карточки рекомендуемых блюд (горизонтальные/вертикальные по переключателю)
- В Network — `POST /chats/{id}/messages`, `Content-Type: text/event-stream`, события `meta`/`token`/`done`

### CHAT-3 — Соответствие после reload

**Шаги:**
1. После CHAT-2 — F5

**Ожидаемый результат:**
- История загружается полностью
- Карточки рекомендуемых блюд совпадают с теми, что были после стрима
- Welcome-сообщение по-прежнему первым

### CHAT-4 — Новый чат

**Шаги:**
1. Кликнуть на иконку SquarePen в шапке

**Ожидаемый результат:**
- Запрос `POST /chats`, история обнуляется, остаётся только welcome
- Старый чат сохранён, доступен через `GET /chats`

### CHAT-5 — Mock-режим

**Предусловие:** бэкенд не запущен.

### ADMIN-PR-API — Промпты на реальном бэке

**Предусловие:** бэкенд запущен, миграция `000008_prompts_decomposition` применена, юзер залогинен админом (через `/login` с админ-email).

**Шаги:**
1. Открыть `/admin/prompts`.
2. В DevTools → Network проверить `GET /admin/prompts` и три `GET /admin/prompts/details?name=...`.
3. Изменить контент → «Сохранить черновик».
4. Открыть админскую вкладку → клик «Тестировать в чате» → отправить сообщение → вернуться в админку.
5. «Раскатить на всех» → подтвердить.
6. В истории нажать «Откатить» у предыдущей версии.

**Ожидаемый результат:**
- На загрузке страница показывает три промпта (system / classification / refusal) с реальными версиями из БД.
- «Сохранить черновик» → `PUT /admin/prompts/draft?name=<name>` → 200, у промпта в списке появляется бейдж «Есть черновик».
- «Раскатить» → `POST /admin/prompts/publish?name=<name>` → версия активной увеличивается; черновик исчезает.
- «Откатить» → `POST /admin/prompts/rollback?name=<name>&version=<v>` → новая активная версия; в истории — новая запись с тем же содержимым.
- Редактирование контента <50 символов или без `{{user_message}}` (для classification/refusal) → 400 `prompt_invalid`, кнопка «Сохранить черновик» задизейблена.
- В mock-режиме (бэкенд выключен) поведение прежнее: in-memory мутации.

### ADMIN-CRUD-API — CRUD-страницы на реальном бэке

**Предусловие:** бэкенд запущен, миграции применены, юзер-админ залогинен.

**Шаги (Категории `/admin/categories`):**
1. Открыть страницу — должно быть `GET /categories`. Видим реальные категории из БД.
2. «+ Добавить категорию» → имя «Тест» → Сохранить → `POST /admin/categories` → строка появляется в списке.
3. Toggle «Доступна» у любой категории → `PATCH /admin/categories/{id}` с `{is_available}`.
4. Удалить пустую категорию → `DELETE /admin/categories/{id}` → 204. Категорию с блюдами удалить нельзя — alert «category_has_dishes» (409 от бэка).

**Шаги (Теги `/admin/tags`):**
1. `GET /admin/tags` на mount.
2. Add/Edit/Delete → соответствующие POST/PATCH/DELETE. Slug генерируется из имени.

**Шаги (Меню `/admin/menu`):**
1. Список грузится из стора (он сам грузит `/categories` + `/menu` на initSession).
2. Toggle «В меню» → `PATCH /admin/menu/{id}` с `{is_available}` → store перетягивает меню (`refreshMenu()`).
3. Trash → `DELETE /admin/menu/{id}` → soft delete, блюдо пропадает из выдачи `available=true`.
4. «+ Добавить блюдо» → форма → Сохранить → `POST /admin/menu` с `category_id` (вычисляется из имени категории через подгруженный список).
5. Pencil у блюда → `PATCH /admin/menu/{id}` со всеми изменёнными полями.

**Шаги (Заказы `/admin/orders`):**
1. На mount: `GET /admin/orders?limit=200` (без status-фильтра).
2. Поменять «Любой статус» → «Готовится» → `GET /admin/orders?status=cooking&limit=200`.
3. Кликнуть строку, в дровере «→ Готов» → `PATCH /admin/orders/{uuid}/status` с `{status: 'ready'}` → бейдж и список обновляются.
4. Запись о смене статуса автоматически появляется в `GET /admin/orders/{uuid}/actions` (таб «История» в том же дровере).

**Ожидаемый результат во всех:**
- В Network — только реальные API-вызовы (`/admin/...`), `recordAction` локально не пишется.
- При недоступности бэка фронт переходит в mockMode — те же страницы работают на in-memory моках без сетевых запросов.
- Спиннер при загрузке, плашка-ошибка при сетевой ошибке.

### ADMIN-CAT-ROLE — Роль категории в RAG (mock + API)

**Контекст:** в админке категорий появилось поле `role` (`none` / `main` / `companion`). При переименовании категории через PATCH бэк автоматически переиндексирует Qdrant.

**Шаги (mock):**
1. Открыть `/admin/categories`, убедиться, что в столбце «Роль в RAG» у каждой категории отображается значок: «Основная» (янтарный), «Сопровождение» (синий) или прочерк.

3. Открыть только что созданную категорию через ⏘ в строке, переключить роль на «Сопровождение». Сохранить — увидеть в audit-моке запись `Роль: Основная → Сопровождение`.

**Шаги (API, mockMode выключен):**
1. Аналогичные шаги в реальном режиме — после сохранения категория перезагружается с актуальным `role` из бэка.
2. Переименовать существующую категорию (например, «Супы» → «Супы и бульоны»). В консоли бэка проверить наличие лога `reindex category: done`. После этого выполнить чат-запрос «что-нибудь горячее» — categoria уже отдаётся с новым именем.
3. Попробовать PATCH с невалидным `role` через DevTools/Postman → ожидать `400 invalid_category_role`.

**Ожидаемый результат:**
- Селект и столбец «Роль в RAG» отображаются и сохраняют выбор.
- В audit-моке/реальном audit-логе виден переход роли между значениями.
- Переименование категории через админку → бэк автоматически реиндексирует Qdrant (без `make embed-menu` вручную).
- Невалидные значения роли возвращают 400, форма не разрушается.
